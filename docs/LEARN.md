# Known-issue store and `dmesg-agent learn`

Community ground truth (lore, bugzilla, launchpad, distro trackers) distilled
into a small, searchable "known issues" library, so diagnosis can hit "this is
upstream bug #X, fixed by commit abc123" instead of re-deriving it every time.

## The three-level index (MMU-style)

```
L1 subsystem    storage / memory / gpu / network / locking / ...
L2 fault_class  oom / nvme / ata / soft-lockup / ...   (triage signature names)
L3 fingerprint  struct key = {sig, dev, codes}          exact match, then token sim
```

The taxonomy is **generated by the same code that classifies a live dmesg**
(`triage.SIGNATURES` → `playbooks.SIGNATURE_TO_SUBSYSTEM` →
`knowledge.evidence_fingerprint`). That is the point: an ingested issue lands in
exactly the signature/fingerprint space a diagnosis will query, so recall is a
three-step index lookup, not a full-corpus search.

## Storage: small on purpose

Only the index + a one-line summary + an external pointer are stored. The full
thread/patch text is never kept.

| field | purpose | bound |
|---|---|---|
| fingerprint + tokens | retrieval (L3) | 40 tokens |
| subsystem + fault_class | L1/L2 index | — |
| title / root_cause / fix | offline summary | 140 / 200 / 120 chars |
| urls | external pointer | — |

One record ≈ 0.6 KB; duplicate sources of the same fingerprint merge into one
row with multiple URLs. `tests/test_knownissues.py::test_record_is_tiny` guards
the size budget.

## Ingesting (stage 1)

### Bulk search — no message IDs needed (recommended)

lore's search results mbox is served from a **POST form** (`x=m` is ignored on
GETs; a GET returns the HTML page). `--lore-search` does the POST for you, so
you only provide a query:

```bash
dmesg-agent learn --lore-search 'nvme timeout' --limit 1000 --verbose
dmesg-agent learn --lore-search 'NV_ERR_NO_MEMORY' --full-threads --max-download-mb 64
```

- One search pulls every matching mail — no message-id to collect.
- Broad terms can yield hundreds of MB; the download is capped by
  `--max-download-mb` (default 128) with a clear error.
- `--full-threads` uses lore's "full threads" form field; default is results
  only.
- `.mbox.gz` is decompressed automatically; HTML pages are rejected.

Manual alternatives (same data): a thread mbox
`https://lore.kernel.org/all/<message-id>/t.mbox.gz` (needs an ID, single
thread only), or a direct search POST with
`--data-urlencode 'z=results only' '...?q=…&x=m'`. A git clone of
`https://lore.kernel.org/all/` is the future full-archive adapter.

### Automatic catalog — `learn --auto`

Rather than one command per topic, `--auto` walks
`dmesg_agent/ingest_catalog.py`: one targeted lore query per high-value fault
class/subsystem plus kernel.org Bugzilla queries, using the same L1 subsystem
names as diagnosis.

```bash
dmesg-agent learn --auto --auto-max-mb 512
dmesg-agent learn --auto --extract --max-extract 200
dmesg-agent learn --auto --loop --interval 86400
```

- `--auto-max-mb` caps the total lore download per pass (default 512); each
  entry also has its own per-year `max_mb`. `--auto-max-queries N` runs a
  prefix and `--auto-only ID` (repeatable) runs selected entries (useful for
  smoke tests or topping up one subsystem). Failures are per-entry warnings.
- Lore's mbox endpoint ignores pagination offsets, so each catalog query is
  split into calendar-year windows (`d:YYYY0101..YYYY1231`) scanned newest
  first, with `--auto-since-year` (default 2018) as the floor. A window with
  no matching mail is skipped, not treated as an error.
- Resolved Bugzilla bugs keep their whole comment thread (bounded), so
  "fixed by commit …" reaches the extractor; lore patches carry `Fixes:`
  trailers. Launchpad/GitLab remain explicit `--tracker-query` sources.
- Extraction stays inline and capped per run (`--max-extract`); repeated or
  `--loop` runs re-see pending records and fill gaps, while source-id and
  fingerprint dedup prevent duplicates. Fix records therefore accumulate over
  runs without a separate state machine.
- `tests/test_ingest_catalog.py` pins the main subsystem coverage and entry
  shape.

### Quality filters and dedup

`learn` drops: release announcements, stable-review cover letters (000/816),
Yocto/OE version bumps, `[GIT PULL]`/`[PULL]`/`[ANNOUNCE]`, CVE/digest mails, CI.Hooks/patchwork notifications,
and pure discussion with only a generic signature and no log line. It keeps
specific patches and classified issues.

Dedup is three-tier: `(source, source_id)` idempotency; normalized patch-series
titles merge v1/v2/v3 and `Re:` mails (one record, many URLs); structural
fingerprints merge cross-source duplicates.

`--db PATH` overrides the store location (default
`$XDG_DATA_HOME/dmesg-agent/known-issues.db`). `--since` filters by the mail
`Date`; `--loop --interval SEC` re-scans for continuous updates.

## Querying / browsing (the taxonomy tree)

```python
from dmesg_agent.knownissues import KnownIssueStore
s = KnownIssueStore()
s.stats()                    # L1/L2 bucket counts
s.list(subsystem="storage")  # every class under storage
s.list("storage", "ata")     # the L3 bucket for ata
s.get(42)                    # one record with root_cause/fix/urls
s.search(fingerprint=fp, fault_classes=["nvme"], subsystems=["storage"],
         tokens=tokens)      # diagnosis-time recall ranking
```

A `dmesg-agent known-issues` command plugin (browse/manage) and the
`known_issue_lookup` context plugin (diagnosis-time recall) are the next
stages.

## Stage 2: LLM extraction (`--extract`)

```bash
dmesg-agent learn --mbox thread.mbox.gz --extract --max-extract 25 --verbose
dmesg-agent learn --lore-search 'nvmet-tcp TLS handshake timeout' \
  --extract --provider local --base-url http://127.0.0.1:8080
```

- Uses the configured LLM (same provider/config as diagnosis) on new or
  still-pending records; already-extracted records are skipped, so rerunning
  fills gaps instead of re-paying.
- Fills `symptom`, `root_cause`, `fix` (`commit` / `upgrade_to` /
  `workaround`), `confidence`, and `log_snippets`.
- Anti-hallucination: every `log_snippet` must match the source text verbatim
  (same normalization as verify.py), and a `fix.commit` must appear in the
  source; invented snippets/hashes are dropped and reported in `--verbose`.
- `--max-extract N` caps LLM attempts per run, including failures (default 25; `0` = all). Extraction
  is the slow part — for local thinking models set
  `DMESG_AGENT_EXTRA_BODY='{"chat_template_kwargs":{"enable_thinking":false}}'`
  during extraction.
- Inspect with `KnownIssueStore.get(id)` (`symptom`, `root_cause`, `fix`,
  `log_snippets`, `confidence`, `extraction_model`).

## Stage 3: public bug-tracker REST adapters

`--tracker-query QUERY` drives the REST sources; each source is optional and
repeatable, and results flow through the same `classify → noise filter →
dedup → (optional) extract` pipeline as lore mail:

```bash
dmesg-agent learn --tracker-query 'nvme timeout' \
  --bugzilla https://bugzilla.kernel.org \
  --bugzilla https://bugzilla.redhat.com \
  --launchpad \
  --gitlab https://gitlab.gnome.org/GNOME/mutter \
  --tracker-limit 25
```

- **Bugzilla** (kernel.org, Fedora): `/rest/bug?quicksearch=…` plus comment 0
  (the reporter's log excerpt). Source label `bugzilla:<host>`, URL
  `show_bug.cgi?id=…`. Public bugs only; no API key.
- **Launchpad**: `bugs.searchTasks` on `api.launchpad.net`, then each matched
  bug's title/description; searches all statuses.
- **GitLab**: `/api/v4/projects/<url-encoded path>/issues` with `state=all`
  (open and closed); `--gitlab-token` or `GITLAB_TOKEN` for private projects.
- Comment/detail requests are sequential (one per matched bug), so progress is
  printed and a 120 s per-source budget stops the detail phase; remaining
  Bugzilla bugs stay summary-only and Launchpad bugs stay title-only.
- A failing source is a per-source warning; the other sources still ingest.

All adapters send a fixed honest User-Agent and only read public APIs.

## Stage 4: diagnosis-time recall

The `known_issues` context plugin runs after triage in every diagnosis
(`dmesg_agent/plugins/context_known_issues.py`):

1. classifies the selected log blocks with `classify_text` (the same rules as
   ingest);
2. calls `KnownIssueStore.search()` — exact fingerprint 100, same fault class
   40, same subsystem 10, token Jaccard ≥ 0.25 adds up to 50; subsystem-only
   matches are dropped as too weak;
3. injects up to four records (title, known cause, fix, first URL) into the
   analysis prompt, explicitly marked **external reports — not evidence**.
   The model may use them to sharpen root cause/next steps, but every
   `evidence.quote` must still come from this host's log or collected output.

Each suspicious segment is classified separately, so a firmware block cannot
be lost behind an earlier thermal signal, and generic buckets
(`warning`/`fault`/`driver`) never count as a similarity class. The model is
asked to declare `known_issue_usage` per injected id (`applied` / `considered`
/ `rejected` + why); the report's **Appendix: community known-issue recall**
shows those declarations next to the match reason, source segment and upstream
link. Zero matches and a missing store are reported explicitly, so "the
community store made no difference here" is visible instead of implied.

Flags: `--known-issues-db PATH` (or `DMESG_AGENT_KNOWN_ISSUES_DB`) and
`--no-known-issues`. With no store present the plugin is a no-op, so a fresh
install behaves exactly as before.

## Stage 5: scheduled ingestion

`.github/workflows/known-issues.yml` runs weekly (and on demand): installs the
package, runs the same `--auto` catalog against lore and Bugzilla (512 MB
budget), checkpoints the SQLite WAL, and uploads the store as the
`known-issues-db` artifact. Download it and pass `--known-issues-db`;
extraction stays local because it needs the configured LLM
(`dmesg-agent learn --auto --extract`).

## Still open

- **lore full-archive adapter**: `git clone https://lore.kernel.org/all/` plus
  incremental `git pull`, instead of per-query downloads.
- **CI extraction**: the scheduled workflow has no LLM credentials, so it
  ingests issues/fingerprints only; fixes are extracted by a local
  `learn --auto --extract` (or a future secret-backed workflow step).
- **SQLite FTS** if the store grows past a few tens of thousands of records
  (`search()` currently scans the compact table).
- **Multi-label ranking**: a reply quoting an unrelated signature can still
  land in a secondary L1 bucket; title-specific routing covers the common case.

## Etiquette / compliance

Use the official APIs and public archives — no scraping, no user-agent
spoofing. A fixed, honest User-Agent is set by the tool. Bug trackers are
queried through their REST APIs with a per-source cap (`--tracker-limit`) and
comment fetches only for matched bugs. For lore, prefer
`git clone https://lore.kernel.org/all/` and incremental `git pull` over
re-downloading.
